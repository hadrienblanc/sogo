# Ticket 5910 — "Some parameter not supported for a mime type"

## Verdict: NOT a bug (in SOGo) — upstream SOPE diagnostic, parsing is correct

The reporter is right on both counts: the two parameters are harmless and the
message is a false alarm. What happens:

- The triggering mails carry a `Content-Type: text/plain; charset=…;
  type="multipart/alternative"; boundary="_004…_"` — a multipart that a
  gateway/client flattened into a text part without stripping the obsolete
  `type`/`boundary` parameters of the former multipart container (the
  `_004…_` boundary shape is generated by Exchange). This was confirmed live:
  Dovecot relays those parameters verbatim in `BODYSTRUCTURE`
  (`("charset" "us-ascii" "type" "multipart/alternative" "boundary" "_004…")`
  for an appended `test-5910-*` message on the shared stack).
- RFC 2045 §4 makes Content-Type parameters an extensible namespace:
  unrecognized parameters **MUST be ignored**. SOPE does exactly that —
  `NGConcreteTextMimeType initWithType:subType:parameters:`
  (`sope/sope-mime/NGMime/NGConcreteMimeType.m:100-180`) models the
  parameters it knows (`charset`, `name`, `format`, `method`, `reply-type`,
  `delsp`, `q`, `x-*`) and skips the rest. The parsed type keeps
  `text`/`plain`/`charset=us-ascii` and the message renders fine.
- The log line itself is an **unconditional `NSLog`** at
  `sope/sope-mime/NGMime/NGConcreteMimeType.m:171-174` (and a sibling for
  `application/*` at `:461-464`) — i.e. a diagnostic from the **upstream SOPE
  library**, printed for every parameter SOPE does not model. All comparable
  parser diagnostics in SOPE (`NGMimeUtilities.m:87-222`) are gated behind
  the `MimeLogEnabled` user-default; only these two are not. That verbosity
  mismatch is the actual defect behind the log noise and belongs to the
  SOPE repo (`~/…/sogo/sope`, built into the e2e image via `COPY sope/`),
  which does not flow through SOGo PRs.

Both production paths were reproduced locally against the same SOPE build
SOGo links (`local/root/usr/lib/libNGMime.so`), yielding the exact reported
output:

- IMAP listing/prefetch: BODYSTRUCTURE params →
  `NGImap4Message+BodyStructure.h:238 _buildMimeBodyPart` →
  `[NGMimeType mimeType:subType:parameters:]` — logs both lines with clean
  values (this runs on every mailbox refresh, hence "often");
- full-message parse (message view): the folded header keeps fold
  whitespace inside the quoted boundary
  (`NGMimeUtilities.m:160-176` accepts CTLs in quoted values), which is
  what the multi-line values in the report show (`_004␉7eb61e…␉`; the
  leading `text/*` lost its `*` to Mantis markdown pairing the two `*`
  across lines).

The reporter's second ask — print the mail ID in the message — is not
implementable from SOGo either: the log site sits inside libNGMime with no
mail/folder context (SOPE has no notion of UIDs), and the SOGo build links
the prebuilt upstream SOPE.

## What changed

Nothing in product code — the ticket is proven not to be an SOGo bug
(parsing outcome is correct per RFC 2045 §4, no data loss, no crash, mail
renders). Per policy, the worth-locking behavior is covered by tests only:

- `Tests/Unit/TestNGMimeTypeUnknownParameters.m` (new, 3 tests):
  - `test_unknownParametersOnTextType` — the exact ticket header through the
    raw-string parser;
  - `test_foldedUnknownParametersOnTextType` — same header folded inside the
    quoted boundary value;
  - `test_bodyStructureParametersOnTextType` — the Dovecot/BODYSTRUCTURE
    triplet instantiation.
  All three assert: type `text`, subtype `plain`, charset `us-ascii`
  preserved; `valueOfParameter:` returns `nil` for `type`/`boundary`; and
  `stringValue` regenerates `text/plain; charset=us-ascii` without leaking
  the stale parameters into re-emitted headers.
- `Tests/Unit/GNUmakefile` — registers the test file.

AVANT (behavior, unchanged and now locked): broken mail logged a scary
two-line diagnostic on every mailbox prefetch and every message view, while
being parsed correctly.
APRÈS: same correct behavior, regression-guarded; the diagnostic itself can
only be silenced upstream (SOPE) by gating the `NSLog` behind
`MimeLogEnabled` like its sibling parser warnings — recommended follow-up
in the `sope` repo (one-line change ×2 in `NGConcreteMimeType.m`).

## PR body draft

**test(mail): lock tolerance of unknown text/* Content-Type parameters (bug 5910)**

Mantis 5910 reports recurring `MimeType 'text/*' does not support a
parameter named 'type'/'boundary'` lines in sogod logs and asks whether the
parameters are valid and whether the message could name the offending mail.

Investigation (live IMAP reproduction against Dovecot + a harness on the
SOPE build we link) shows this is not an SOGo defect: the triggering mails
carry a flattened multipart's leftover `type` and `boundary` parameters on
a `text/plain` Content-Type, Dovecot relays them verbatim in BODYSTRUCTURE,
and SOPE parses them the way RFC 2045 §4 mandates — unrecognized parameters
are ignored while `text`/`plain`/`charset` are preserved, so the message
renders correctly. The log line is an unconditional diagnostic inside the
upstream SOPE library (`NGConcreteTextMimeType`), emitted for every
parameter SOPE does not model; it cannot be extended with the mail UID from
the SOGo side since libNGMime has no mail context. The proper silence-fix
(gating the `NSLog` behind `MimeLogEnabled`, like all other SOPE parser
warnings) belongs to the SOPE repository.

This change therefore locks the tolerance behavior in the unit suite —
raw-header parse, folded-header parse and BODYSTRUCTURE-driven
instantiation — so a future SOPE/SOGo regression that would drop the
charset, crash, or leak the stale parameters into regenerated headers
cannot land unnoticed.
